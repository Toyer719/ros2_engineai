3. ETAT DE MOUVEMENT REQUIS : lower_body_balance
-----------------------------------------------------
/motion/joint_override_command (utilise par tous ces scripts, via lever.py)
n'a d'effet QUE sur les bras, et QUE si le robot est en mode
"lower_body_balance". En pd_stand la commande est acceptee mais RIEN ne
bouge. levee.py bascule lui-meme dans ce mode au demarrage (donc
rien a faire a la main pour celui-la). Pour un script qui ne le fait pas
(move_arms_demo.py, test_leg_override.py), basculer a la main d'abord :

    python3 /home/user/source/engineai_workspace/src/interface_example/scripts/switch_to_target_motion_example.py --target-motion lower_body_balance

Si le robot part de joint_bridge, il n'y a pas de transition directe vers
lower_body_balance -- repasser d'abord par pd_stand (le script ci-dessus
gere ca automatiquement pour levee.py, --detour pd_stand).

Pour tout arreter d'urgence : bouton "passive" de la telecommande (LB+RB).
Coupe tout mais rend le robot MOU (il s'affaisse) -- dernier recours, pas
un arret propre.

Pour la MARCHE (marche.py, cf section 5b) : le script bascule
lui-meme lower_body_balance -> rl_terrain avant de publier une vitesse, PUIS
rebascule en lower_body_balance a la fin -- rien a faire a la main non plus.
INCONNUE NON VERIFIEE au 2026-08-28 : la transition directe rl_terrain ->
lower_body_balance existe-t-elle, ou faut-il un detour ? Le premier essai
reel (motion-state-switch-only, --forward 0.0) sert justement a repondre a
cette question -- si ca echoue, verifier `ros2 topic echo /motion/motion_state
--once` en rl_terrain pour voir available_transition_motions et ajuster
--walk-motion-state ou le detour dans motion_state.py.

5b. MARCHE (marche.py) ET SEQUENCE COMBINEE (orchestrateur.py)
---------------------------------------------------------------------------------
walk_real.py (ancien canal LCM/manette virtuelle) est CONFIRME MORT sur le
robot reel (2026-08-27/28, cf son bandeau d'avertissement) -- NE PLUS
UTILISER. marche.py le remplace : publie /motion/body_vel_cmd
(vraies unites m/s / rad/s, PAS l'echelle -1..1 de l'ancien stick manette).

Premiers essais reels le 2026-08-28 -- resultats ci-dessous, a lire avant de
retester :

    cd /home/user/projects/arm_test

    # 1) dry-run, rien n'est envoye
    python3 marche.py --dry-run --forward 0.12 --duration 1.0

    # 2) bascule d'etat seule, vitesse ZERO -- le robot ne doit PAS bouger,
    #    ca valide juste que rl_terrain est atteint puis lower_body_balance
    #    est regagne (repond a l'inconnue notee en section 3 -- CONFIRME : la
    #    transition rl_terrain -> lower_body_balance se fait direct, sans
    #    detour, cf logs "[ETAPE] mode lower_body_balance actif." en sortie)
    python3 marche.py --forward 0.0 --duration 1.0

    # 3) tout petit mouvement reel -- 0.12 CONFIRME TROP FAIBLE (voir note)
    python3 marche.py --forward 0.12 --duration 1.0

RESULTAT DU 2026-08-28 : etapes 1 et 2 OK (etat bascule proprement dans les
deux sens, aucune erreur). Etape 3 (--forward 0.12) : le robot reagit
(leger ajustement de posture visible en rl_terrain) mais NE MARCHE PAS --
teste avec duration=1.0s ET duration=3.0s, meme resultat, donc pas un
probleme de duree. En montant a --forward 0.45 : premier pas reel obtenu,
le robot marche. Le seuil exact entre 0.12 et 0.45 n'a pas ete cherche.
DEFAULT_FORWARD_MPS dans marche.py est maintenant 0.45 (etait
0.12, jamais valide). QoS du topic verifiee au passage (ros2 topic info -v
/motion/body_vel_cmd sur Nezha) : BEST_EFFORT/VOLATILE des deux cotes,
compatible -- ce n'etait donc pas un probleme de QoS, juste de magnitude
trop faible pour declencher un cycle de marche.

Sequence complete marche + levee (orchestrateur.py), phase par phase,
JAMAIS d'un coup au premier essai :

    python3 orchestrateur.py --only-phase marche --forward 0.12 --duration 1.0

    python3 orchestrateur.py --only-phase levee --lift-only-phase serrage
